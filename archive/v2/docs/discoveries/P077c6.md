## Root cause pinned — evidence

`TempFixture::new` (`parity.rs:116-124`, pre-fix) keyed its throwaway directory name on `process::id() + SystemTime::now().as_nanos()` only:

```rust
let dir = std::env::temp_dir().join(format!("sos-parity-{name}-{}-{nanos}", std::process::id()));
```

Two facts, both measured (not assumed), made this non-unique in practice:

1. **Shared pid.** All test functions inside one `cargo test` binary run as **threads inside a single OS process** — `std::process::id()` is identical for every parallel test in that binary. Confirmed via instrumentation: every `[DIAG] TempFixture::new` log line in every captured run showed the same `pid=<N>` across all threads.
2. **Coarse clock resolution.** Measured directly on this machine: a tight sequential loop of 200,000 `SystemTime::now().as_nanos()` calls returned an *identical* value on 195,032 of them (~97.5%). The nanosecond field in the API does not imply nanosecond hardware resolution.

Combined: under real thread parallelism, two independent `build_new_fixture()` calls — one from `parity_new_enforced`, one nested inside `parity_adopt_enforced`'s `build_adopt_fixture()` — can sample the identical nanos value at nearly the same instant and produce the **identical** `TempFixture` directory path. Instrumented proof, captured in all 4 failing runs (log excerpt, `diag_fail_12.txt`):

```
[DIAG] TempFixture::new name=new pid=42474 nanos=1784721757242650000 dir=".../sos-parity-new-42474-1784721757242650000" thread=ThreadId(7)
[DIAG] TempFixture::new name=map pid=42474 nanos=1784721757242650000 dir=".../sos-parity-map-42474-1784721757242650000" thread=ThreadId(6)
[DIAG][COLLISION] dir already existed BEFORE create_dir_all: ".../sos-parity-new-42474-1784721757242650000"
...
[DIAG] pre-adopt-invoke kit=".../sos-parity-new-42474-1784721757242650000/new-fake-kit" worker.md_exists=true install-hooks_exists=true phieu-readme_exists=true
[DIAG] TempFixture::drop dir=".../sos-parity-new-42474-1784721757242650000" thread=ThreadId(7)
[DIAG] post-adopt-invoke kit=".../sos-parity-new-42474-1784721757242650000/new-fake-kit" worker.md_exists=false install-hooks_exists=false
```

Both `TempFixture` instances (thread 5's and thread 7's `build_new_fixture()` calls, one feeding `parity_new_enforced` directly, the other feeding `parity_adopt_enforced` via `build_adopt_fixture()`) believed they owned that identical directory. Thread 7's `Drop` (`fs::remove_dir_all`) fired WHILE thread 5/adopt's `sos adopt` subprocess (`Command::output()`) was still running against the SAME shared kit path — wiping the directory's spine files out from under the still-in-flight adopt invocation. `pre-adopt-invoke` showed spine present; `post-adopt-invoke` (same test, same run) showed spine gone, with the colliding `Drop` sandwiched exactly in between. Identical pattern in all 4 captured failures (runs 2, 4, 12, 20 across two batches).

## Fixture-race vs production-race — classification

**Pure fixture-race, test-harness-only.** No production code path (`src/commands/adopt.rs`/`new.rs`/`sync.rs`, `bin/sos.sh`) participates in or is affected by this race — each is invoked as an isolated child process per test. Fix scope = `crates/sos-cli/tests/parity.rs` only.

## Fix applied

`TempFixture::new` now mixes a process-wide monotonic `AtomicU64` counter (`fetch_add(1, Ordering::Relaxed)`) into the directory key:

```rust
static TEMP_FIXTURE_COUNTER: std::sync::atomic::AtomicU64 = std::sync::atomic::AtomicU64::new(0);
// ...
let counter = TEMP_FIXTURE_COUNTER.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
let dir = std::env::temp_dir().join(format!(
    "sos-parity-{name}-{}-{nanos}-{counter}",
    std::process::id()
));
```

This guarantees uniqueness independent of clock resolution — no two `TempFixture`s in the same process can ever resolve to the same path, regardless of how many threads race `SystemTime::now()` at the same instant. No new crate dependency (ruled out reaching for `tempfile` — an atomic counter is the cheapest fix that fully closes the gap).

**KHÔNG sorted anything, KHÔNG touched `src/commands/*.rs`, KHÔNG touched `bin/sos.sh`, KHÔNG touched any golden.**
