# Discovery — P078c: render-before-toolgate split

## Anchors #1-7 — verification result

- **#1 per-runtime fn shape (CORRECT):** `install.rs:24-125` (pre-P078c) had 2 separate fns
  `run_claude()`/`run_codex()`, both identical 3-step shape `plan()→resolve_tools()?→apply()/
  dry_run()`. Confirmed at `install.rs:47` (claude `?`) and `install.rs:93` (codex `?`).
  Refactored during EXECUTE into a single shared `run_adapter(&dyn Adapter, owner, runtime_label,
  dry_run, require_tools)`, called by both `run_claude()`/`run_codex()` — symmetric behavior is
  now structural (one code path) rather than hand-maintained parity between two fns.
- **#2 `resolve_tools()` signature (CORRECT):** `engine.rs:308` `pub fn resolve_tools() ->
  Result<Vec<crate::tools::ToolStatus>>`. Pre-P078c called via `?` (hard-fail-and-abort). P078c:
  still called via `?` when `--require-tools` is set (fail-fast path, unchanged behavior);
  default path no longer calls `resolve_tools()` at all — instead calls the lower-level,
  non-`Result` `tools::check_tools()` + `tools::required_drift()` + `tools::describe_failure()`
  directly (see below), avoiding a match-on-`Result` workaround entirely.
- **#3 `apply()`/`dry_run()` independence (CORRECT, stronger than assumed):** `engine.rs:186`
  `apply(project_root, plan, owner, source_version)` and `engine.rs:148` `dry_run(project_root,
  plan)` — neither takes tool status as input. `engine.rs:183-185`'s own doc comment explicitly
  states: "Step 5 (tool-resolve) is intentionally NOT called here ... the CLI wires it as a
  separate no-op step so this function stays pure transaction-execution." This is a direct
  in-code confirmation (not an inference) that the reorder is architecturally safe and requires
  zero `sos-install` engine change.
- **#4 exit-code mechanism (CORRECT — chosen: `std::process::exit(3)`):** `main.rs` returns
  `anyhow::Result<()>` uniformly; the default Rust `Termination` impl exits 1 on `Err`. Rather
  than plumb a custom `ExitCode`/exit-hint through `main.rs`, `commands/tools.rs:51` and
  `commands/launch.rs:34` already call `std::process::exit(1)` directly inside a command
  function — an established codebase pattern. P078c extends this: `report_tool_drift()` in
  `install.rs` calls `std::process::exit(3)` directly after printing the warning. This is
  simpler than the phiếu anticipated ("possibly main.rs" hedge) — **`main.rs` did NOT need any
  change beyond the new `--require-tools` clap field**, and no existing `?`/`Result` handling
  elsewhere was touched.
- **#5 `sos tools status` unchanged (CORRECT, regression-verified):** `commands/tools.rs` was not
  touched. Live run on this machine: `sos tools status` → table + `exit 1` on required drift,
  unchanged.
- **#6 OA-07 intent (CORRECT):** confirmed against `docs/retro/OUTSIDER_AUDIT_SYSTEM_GAPS_2026-07-22.md`
  — intent is "surface drift loud", not "block render". Preserved: default path warns loud +
  exits 3 (never silent); `--require-tools` restores full fail-closed abort for callers that want
  the strongest guarantee.
- **#7 CodexAdapter.plan() target paths (CORRECT, plus a stale-comment fix):** `templates.rs:87-103`
  confirms real target paths `AGENTS.md`, `.codex/agents/*.toml`, `.codex/config.toml`,
  `.codex/hooks.json`, `.codex/rules/exec-policy.rules`, `.agents/skills/*/SKILL.md`,
  `scripts/codex/*.sh` (17 total, `lib.rs:401` test `plan_renders_seventeen_artifacts`).
  `install.rs`'s old comment claiming CodexAdapter.plan() "is still a b1 stub" was stale post
  P078a/b (Codex render has been real since P078b2/b3) — fixed in this phiếu (Tầng-2 doc-rot,
  not an architectural finding).

## Reorder soundness

`apply()`/`dry_run()` verified fully independent of `resolve_tools()`/tool status — both by
reading the code (neither function's signature takes tool state) and by the engine's own doc
comment explicitly stating tool-resolve is wired as a separate step by the CLI. No `sos-install`
change was required.

**Bonus discovery:** `tools::gate_required()` (called internally by `resolve_tools()`) already
had non-aborting siblings, all already `pub`: `tools::check_tools()` (pure `Vec<ToolStatus>`, no
`Result`), `tools::required_drift()` (bool), `tools::describe_failure()` (message string). This
meant Task 1's "capture-don't-propagate" requirement needed **zero new engine/tools code** —
`install.rs`'s `report_tool_drift()` calls these three directly, reusing the exact same message
text `sos tools status`/`resolve_tools()` already produce. `git diff crates/sos-install/` is
empty, satisfying Constraint #2 more strongly than the phiếu anticipated (no "additive helper
function" was even needed).

## Exit-code scheme chosen

- `0` = render OK + tools ready.
- `3` = render OK, required-tool drift/missing (`EXIT_TOOLS_NOT_READY` const in `install.rs`) —
  loud stderr WARNING (tool name + expected + found via `describe_failure()`, plus pointer to
  `sos tools status`) precedes the exit call.
- `1` = render/apply actually failed (`?`-propagated `anyhow::Error`, unchanged), OR
  `--require-tools` fail-fast abort (unchanged pre-P078c behavior, gated behind the new flag).

Mechanism: `std::process::exit(3)` called directly inside `report_tool_drift()`, no `main.rs`
plumbing beyond the new clap field. This reuses the exact pattern already present at
`commands/tools.rs:51` and `commands/launch.rs:34`.

## `--require-tools` + `--dry-run` interaction (Tầng-2, self-decided)

Chosen: `--require-tools` gates BEFORE printing the dry-run plan, same as a real run — i.e. drift
under `--require-tools --dry-run` aborts with exit 1 and prints nothing (no plan, no warning).
Rationale: a CI caller passing `--require-tools` wants the strongest fail-closed guarantee
regardless of `--dry-run`; showing the plan first and then failing would be a weaker signal than
what `--require-tools` promises elsewhere. Verified live: `install --runtime codex
--require-tools --dry-run` on this drift machine → same `Err`/exit 1 as the non-dry-run case,
zero output beyond the error, zero files.
