## Worker CHALLENGE Turn 1 finding — engine-vs-adapter seam (O1.1)

`ManagedOperation` (d1 placeholder type, `sos-core/src/adapter.rs`) originally carried only `description: String` + `target_path: String` — no bytes to write. The engine therefore had no trait-pure way to obtain content to write/hash/record; `render()` is a separate trait method with no link back to a `ManagedOperation`. This blocked Task 1 as literally scoped (additive/non-clobber/rollback all require content).

**Architect ACCEPT Alt A** (Worker's own recommendation): narrow amendment — added `content: String` to `ManagedOperation` only. `Adapter`'s 5 methods and `ManagedManifest`'s 6 fields (the phiếu's explicit hard SHAPE) are UNCHANGED. Verified this is sufficient at EXECUTE: engine now computes `sha256(op.content)`, resolves target state, writes exactly `op.content`'s bytes, records `content_hash` in the manifest — no further gap surfaced (no asset-identity indirection needed, since `content` is now self-contained per operation).

## Assumptions in phiếu — WRONG (Tầng-2 self-adapted, no escalation)

- **3-way non-clobber split was insufficient.** The phiếu spec'd `Create`/`Update`(hash==recorded)/`Conflict`. Live EXECUTE (idempotence fixture) exposed that classifying an already-correct target as `Update` still performs `fs::write` (identical bytes) AND bumps `rollback_ref` on every re-run — breaking the phiếu's own idempotence requirement ("`.sos-manifest.toml` byte-unchanged" on 2nd run). Fixed by adding a 4th variant, `Decision::NoOp` (on-disk hash == desired hash → skip entirely, zero mutation, zero manifest touch), checked BEFORE the recorded-hash comparison. This is a Tầng-2 refinement of the engine's own internal decision logic (not a trait/schema/API change) — self-decided, no escalation.
- **`.sos-adopt-incoming` precedent narrower than implied.** Anchor #7 suggested mirroring adopt's non-clobber pattern; only the staging-directory idea carried over — the hash-discrimination logic is new (see anchor #7 above).

## Engine-vs-adapter separation — clean after amendment

## Rollback semantics — snapshot-restore sufficient, escape-hatch did NOT fire

Simple snapshot-before-mutate covers all 3 cases cleanly: CREATE → delete on rollback; UPDATE → restore exact prior bytes (captured via `fs::read` before the overwrite); CONFLICT → no mutation ever happened, nothing to roll back. No staging/2-phase mechanism needed — confirmed live via the rollback fixture (real io error: op 2's target parent path occupied by a plain file, so `fs::create_dir_all` genuinely errors — no artificial fail-injection hook in engine code).
