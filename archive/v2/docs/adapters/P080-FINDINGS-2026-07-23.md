Root cause (`hooks/pre-commit` dev `[8/8]` hook, phases `[6/8]` and `[7/8]`):
both wrap their guard-script call in `if [ -f script ]; then ... else echo
"⏭ missing"; fi` — the `else` branch does NOT increment `FAIL_COUNT`, so a
missing guard script silently downgrades to "allowed." This is the EXACT
"round-4 A3/A4" bug the Codex-side backstop-minimal hook's own header
comment (`hooks/pre-commit` rendered by `sos install --runtime codex`,
confirmed fail-closed — see D2) says was fixed. The fix was applied to the
backstop-minimal hook only; the dev `[8/8]` hook (rendered by `sos new`,
Claude path) still has the old fail-open branches. **This is a genuine
regression/inconsistency between the two runtimes' hook variants — the
Claude-rendered hook is LESS safe than the Codex-rendered one for the same
2 invariants.** Recommend P080x (Tầng 1, Debate) to port the backstop's
fail-closed pattern into `hooks/pre-commit`'s own `[6/8]`/`[7/8]` phases.

### Operational caveats (discovered during Task 3, not failures — record for future dogfood runs)

- **(a) `codex exec` sandbox default is read-only.** The first attempt at C1
  needed `--sandbox workspace-write` — without it the run is vacuous (no
  writes ever attempted, hooks never exercised). This is a required flag for
  any future `codex exec`-based cross-runtime dogfood, not a bug.
- **(b) Hook enforcement is trust-gated, matching `hooks.json`'s own
  description — but the failure mode is SILENT, not loud.** An untrusted repo
  means Codex's PreToolUse hooks do not load at all (no error, no warning) —
  the first C2 attempt on an untrusted repo "leaked" (advance appeared to
  succeed with no block, because the hook simply never fired). Any dogfood
  run against Codex hooks MUST verify the `"hook: PreToolUse ..."` line
  actually appears in output BEFORE trusting a PASS/FAIL verdict — an absent
  hook line means the test is vacuous, not green.
- **(c) `trusted_hash` is content-based**, not path- or install-instance-based
  — it can be (and was, for this Task 3 fixture) cloned between fixtures that
  share the same rendered template content. Convenient for fixture setup but
  worth knowing: trust is a property of file content, not of a specific
  directory/session.
