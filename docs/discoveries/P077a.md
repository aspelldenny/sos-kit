## Golden fixture determinism evidence (2-run identical)

`bootstrap/sos-rs/tests/golden/capture.sh` runs `sos_new/sos_adopt/sos_map/sos_sync` (isolated `bash -c` subshells, since sourcing `bin/sos.sh` sets `set -euo pipefail` in the calling shell — running in-process caused silent abort on the first non-zero internal return; isolating in a subshell per command fixed this) against throwaway fixture repos, normalizes 3 categories of non-determinism, and writes `tests/golden/*.golden`.

Ran `capture.sh` twice independently → `diff -r` of the two output directories was clean (byte-identical) for all 4 `.golden` files.

**Normalization needed (3 categories found):**
1. Absolute paths — fixture target dir + `$SOS_KIT_DIR` printed verbatim → `<TARGET>` / `<SOS_KIT_DIR>`.
2. Dates — `sos adopt`'s first-commit hint embeds `$(date -u +%Y-%m-%d)` → `<DATE>`.
3. **Filesystem-enumeration order** (not anticipated by the phiếu's Task 2 wording, found during capture): `sos new`'s "Category C placeholders to fill (# TODO)" list uses `grep -rl "# TODO" ...` (`bin/sos.sh:583`), which is unsorted — order depends on directory-entry order and flapped between the first 2 raw captures before normalization. `capture.sh`'s `sort_todo_block` fixes this. `sos map`'s surface lists were already sorted at the source (`scan_files()` pipes through `sort`, `bin/sos.sh:296`) — no extra work needed.

## `sos sync` HEAD-pin note (CHALLENGE Turn 1, anchor #7 outcome)

Confirmed via code read + live run: `sos_sync`'s ADDED/UPDATED/FLAGGED classification depends on `_blob_in_history()` walking `git -C "$SOS_KIT_DIR" rev-list --all -- <path>` (`bin/sos.sh:992-999`) — i.e. sos-kit's OWN git history, not just the fixture-repo state. This is semantic non-determinism (can flip a file's bucket across sos-kit commits), not cosmetic. Documented in `tests/README.md`: `sync.golden` was frozen at sos-kit HEAD `d370c82f85a8458e6e23c7208a81054f20d4fba4` (pre-P077a commit); the fixture currently exercises an all-current sync (0 added/0 updated/0 flagged/58 already-current) so near-term drift risk is low, but any future re-freeze of `sync.golden` must record the sos-kit HEAD sha alongside the fixture-repo state — a diff in `sync.golden` alone should NOT be treated as a Rust-parity regression without first checking whether sos-kit's own history moved. This is a Tầng-2 elaboration of the phiếu's existing DISCOVERY escape hatch (Anchor 7), not a new architectural decision — no escalation needed.
