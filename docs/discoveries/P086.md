## Ordering bug found + fixed mid-EXECUTE (Tầng 2 — implementation detail, no design change)

The phiếu's Task 3 spec placed the adopt seed logic ("after the arm-hooks leg, only when `o.status.success()`") textually adjacent to the arm-hooks block, and I initially implemented it there literally. But `adopt`'s actual statement order is: arm-hooks block runs, **then** `init_security()` (which writes `.sos-stack.toml`) runs **after** it. Seeding inside the arm-hooks success branch would run `git add` over `added_paths` **before** `.sos-stack.toml` existed on disk — that one generated file would never get staged for the seed step (though it doesn't affect the trust-gate baseline itself, since `.sos-stack.toml` isn't one of `trust-gate.sh`'s `SURFACE_GLOBS`).

**Fix:** moved the seed step (stage `added_paths` → rebaseline → stage baseline) to run **after** the `.sos-stack.toml` match block, still gated on a `hooks_armed` bool captured from the arm-hooks leg. Applied identically to both `crates/sos-cli/src/commands/adopt.rs` and the bash oracle `sos_adopt` in `bin/sos.sh`. `new.rs`/`sos_new` were unaffected — `new`'s `.sos-stack.toml` write happens earlier (Category B, step [3/4]) than the git-init/seed step ([+]), so `git add -A` already covers it there.

## Design decision confirmed from Debate Log (O1.1, phương án A)

Threaded `added_paths: Vec<PathBuf>` parallel to the existing `added: Vec<String>` display list through every `adopt.rs` call site that writes a real file into `target_dir`: `adopt_item` (both dir-walk and single-file branches), `adopt_skills`, `wire_mcp_json` (both create-if-absent and jq-merge branches), and every inline Category-C/defaults write in `run()` (INVARIANTS.md, AGENT_MAP.yaml, .docs-gate.toml, CHANGELOG.md, ARCHITECTURE.md, BACKLOG.md, .gitignore, .phieu-counter, .sos-stack.toml). One deliberate exception: `.claude/settings.local.json` (via `wire_settings_local`) is **not** pushed to `added_paths` — it's gitignored by design ("per-user, don't commit"; `GITIGNORE_PATTERNS` includes it), so staging it would just print a git "ignored" warning for no benefit. Bash oracle mirrors with a `_added_paths=()` array, same exclusion.

## Edge cases / limitations found

- `.sos-stack.toml`'s rc=2 branch (no stack manifest detected) still **writes** the file (with a hint comment) even though its message goes into the `conflicts` display bucket, not `added`. Per the phiếu's stated criterion ("mỗi call site ghi file thật push path tương ứng"), this file is still pushed to `added_paths`/`_added_paths` regardless of which display bucket its message lands in — the criterion is "was a real file written", not "which list is it echoed into". This is a pre-existing bash-oracle quirk (message wording says "no manifest detected" even though a file WAS written) that this phiếu did not otherwise touch.
- `docs/AGENT_MAP.yaml`'s content-hash line in `adopt.gen.golden` is a CORRECTNESS-oracle exception (P077c5) that `capture.sh`'s `freeze_adopt_gen()` deliberately skips auto-capturing (see its own guard comment). Running `capture.sh` to regenerate goldens for this phiếu silently dropped that hand-verified line — restored it manually (hash unchanged, since P086 touches nothing in the AGENT_MAP.yaml generation path) rather than letting the auto-capture delete it.
- `map.golden.bash-reference` / `map.agent_map.golden.bash-reference` are also written by `capture.sh` as informational side-products (not read by any test, not previously tracked in git). Regenerated then deleted — not part of this phiếu's diff.
