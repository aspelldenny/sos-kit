## Real bug found + fixed mid-EXECUTE (Tầng 2 — implementation only, no design change)

**Symptom:** first `--ignore-scripts` + fallback test failed with `Missing pinned hash file: .../bin/install-sh.sha256` even though the file exists at `.../scripts/install-sh.sha256`.

**Root cause:** `scripts/npm-postinstall.sh` originally resolved its own directory via `dirname -- "$0"`. npm installs `bin` entries (declared in `package.json` `bin` field) as **symlinks** — `bin/sos-kit-setup -> ../lib/node_modules/@aspelldenny/sos-kit/scripts/npm-postinstall.sh`. `dirname "$0"` on a symlink invocation resolves to the symlink's OWN directory (`bin/`), not the real file's directory (`scripts/`) — so `PINNED_SHA_FILE="$SCRIPT_DIR/install-sh.sha256"` pointed at a nonexistent `bin/install-sh.sha256`.

**Fix:** added a `_resolve_self()` helper (portable `readlink` loop, no `readlink -f`/`realpath` dependency assumed since neither is POSIX-guaranteed on all target platforms) that dereferences symlinks before computing `SCRIPT_DIR`. Re-tested: `sos-kit-setup` fallback now correctly locates `install-sh.sha256` and completes the install (verified end-to-end, toolset populated from empty).

This is exactly the class of bug the phiếu's "sh scripts/npm-postinstall.sh" postinstall invocation (run directly, not via npm's bin-symlink mechanism) would NOT have caught — only exercising the actual `npm install`/`bin` symlink path surfaced it. Logged here as the reason nghiệm thu re-ran the tamper + ignore-scripts tests twice (once pre-fix, once post-fix).

- **`sos tools status`** (true-isolated PATH, no real-machine leakage): exit 0. 6 required = OK, 1 optional (advisory-cron) = OK, 3 optional (guard/vps/doc-rotate) = MISSING with `⚠ optional... warn only, exit code unaffected` — matches phiếu's PASS criterion "đủ 10 tool (6 required + 4 optional **tùy availability**)". ## Windows-skip note

`package.json` `"os": ["darwin", "linux"]` causes npm to refuse install on Windows with a clear EBADPLATFORM error at `npm install` time — before postinstall ever runs. This mirrors `install.sh`'s own Windows caveat (Stage 1: `sos` binary not built for `win-x64` yet) — consistent behavior across both distribution paths, no new Windows gap introduced.
