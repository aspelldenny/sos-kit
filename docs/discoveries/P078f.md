## Engine-native vs invoke-script — DECISION: engine-native

**Decision:** engine-native Rust port, NOT a shell-out to `scripts/install-hooks.sh`.

**Reason:** Constraint 1 pointed at the P059/P072 precedent (bash-on-Windows portability risk) — `sos install` must run identically wherever the `sos` binary runs, including Windows environments where a POSIX shell/`bash` may not be on `PATH` (Git Bash is common but not guaranteed, e.g. a bare `cmd.exe`/PowerShell + Git-for-Windows-without-bash-in-PATH setup). Since the `sos` binary is already a native Rust executable, adding a runtime dependency on invoking `bash scripts/install-hooks.sh` would reintroduce exactly the class of platform coupling the Rust port exists to remove. `git` itself is the one external binary assumed present (it's the tool being configured — `sos install` already can't do anything git-related without it), so `git config`/`git rev-parse` are invoked via `std::process::Command::new("git")`, which is cross-platform by construction (the `git` binary handles OS differences internally, not our code). `chmod +x` is done via Rust std `std::os::unix::fs::PermissionsExt` behind `#[cfg(unix)]` (exact pattern already established in this codebase at `crates/sos-cli/src/commands/{adopt,new}.rs`'s `chmod_x()` — reused the idiom, not copy-pasted the function since it lives in a different crate/module), no-op on non-unix (Windows ignores POSIX exec bits; Git for Windows core.fileMode handling is a separate, already-working concern this phiếu doesn't touch).

**`install-hooks.sh` fate:** kept as-is, reference-only, NOT deleted or rewritten (phiếu constraint). It stays useful for repos that install sos-kit content by other means (e.g. hand-copy, not through `sos install`) or that don't build the Rust CLI at all. Noting for future consideration (NOT acted on this phiếu): once `sos install` is the primary distribution path, `install-hooks.sh` may become redundant for `sos`-installed repos — but sos-kit's own self-hosting (this repo) still uses `install-hooks.sh`/`core.hooksPath` directly, so removing it is out of scope and would be its own decision.

## Edge cases / limitations

- **Windows `chmod` no-op:** `chmod_x_if_exists()` compiles to an empty body on non-unix targets (`#[cfg(not(unix))]`). Git for Windows handles the executable bit via `core.fileMode`/its own mechanism; this phiếu does not attempt to replicate that, matching the existing `chmod_x()` precedent elsewhere in this codebase (`adopt.rs`/`new.rs`) which makes the same tradeoff.
- **TTY detection:** `std::io::IsTerminal::is_terminal()` (stable since Rust 1.70, this workspace runs 1.94.1) on `stdin()`. `cargo test` runs with stdin NOT a terminal by default, so the non-clobber test (`hook_arming_non_clobber_aborts_on_foreign_hookspath_non_interactively`) deterministically exercises the fail-closed abort branch without needing to fake a TTY — this is the real CI-safe path, not a workaround.
- **Idempotent guard:** verified by test — a second `apply()` call against a repo whose `core.hooksPath` is already `"hooks"` (our own prior value) does NOT trip the F09 guard (`existing_hp != "hooks"` check), matching Constraint 6 exactly.
- **Hook-arming failure does not roll back the render:** if `arm_git_hooks()` returns `Err` (F09 abort), the manifest has already been saved and files already written (arming runs strictly after `save_manifest()` on the success path — see phiếu anchor #1 insertion point). This is intentional per the phiếu's specified insertion point, not an oversight: the render itself succeeded; hook arming is a separate boundary-activation step that can independently fail (e.g. an adopter's custom `core.hooksPath`) without undoing correctly-rendered files. An adopter hitting the abort still has the rendered `hooks/` content on disk and can resolve the guard manually (unset `core.hooksPath` or re-run interactively to confirm override).
- **No new external dependency:** everything shells out to `git` only (already a hard dependency of any git-tracked project) or uses Rust std — no new crate added to `Cargo.toml`.
