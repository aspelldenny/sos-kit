## O1.1 re-verification (Debate Log Turn 1) — scope correction, not a redirection

O1.1's objection text quoted `new.rs:310` as `copy_tree(&kit.join(".claude/skills")..., true)`. Re-reading the actual code at EXECUTE time: `new.rs:310`'s source is `e.path()` from `fs::read_dir(kit.join("skills"))` — i.e. the **canonical** `skills/<name>/` directory (no symlinks there, confirmed by `adopt.rs:262-263`'s own comment), NOT `.claude/skills`. So `new.rs`'s skill-copy path is actually **not** vulnerable to stub propagation the way O1.1 described.

The REAL propagation risk is `.claude/agents` and `.claude/commands`, copied via `copy_tree(..., deref=true)` at `new.rs:283-284` — these directly source from the kit's `.claude/agents`/`.claude/commands`, which per `agents/README.md`'s convention ARE per-file git symlinks (confirmed: `git ls-files -s .claude/agents/` shows mode `120000` for all 4 files). `adopt.rs:546-547` (`adopt_item(".claude/agents"...)`, `adopt_item(".claude/commands"...)`) has the identical exposure via its own `follow_links(true)` WalkDir (`adopt.rs:199-200`).

This does not change the Chủ nhà-approved option (c) or invalidate O1.1's conclusion ("doesn't change WHICH option, only what 'done' looks like — cover both locations") — it only corrects WHICH subdirectories the stub-detection check needs to actually cover. Implemented `find_symlink_stubs`/`warn_symlink_stubs` (in `new.rs`, `pub(crate)`, reused by `adopt.rs`) scanning all three (`.claude/agents`, `.claude/commands`, `.claude/skills`) for defense-in-depth, called at both the `SOS_KIT_DIR` source (before copy, in both `new.rs` and `adopt.rs`) and the scaffolded target (after copy, `new.rs` only — `adopt.rs` doesn't scaffold a fresh `.claude/agents`/`.claude/commands` tree the same way; its target-side result is covered by the source-side check since `adopt_item` byte-copies whatever the source check already validated).

Tier: Tầng 2 self-decide (implementation detail — which paths a mechanical detection check scans — not an architectural redirect of the Chủ nhà-approved option).

## Stub-detection heuristic (Task 3, option (c))

No reliable cross-platform "was this checked out as a git symlink" signal exists without re-reading `.git/index`. Heuristic used: a path under `.claude/{agents,commands,skills}` that is (a) not a real symlink (`fs::symlink_metadata().is_symlink()` false), (b) not a directory, (c) a short file (<200 bytes, non-empty), (d) single-line content with no whitespace, (e) starts with `..` or `/`. Verified this cannot false-positive against the parity test fixtures — `build_new_fixture()`'s fake `.claude/agents/worker.md` etc. all contain spaces (e.g. `"# fake worker agent\n"`), which fails condition (d).

Non-fatal: prints a warning + fix guidance, does not block scaffolding — matches phiếu wording ("in ra fix").

## Extra discoveries beyond CRLF framing

`.gitattributes`'s `git add --renormalize .` alone does NOT rewrite already-checked-out working-tree files — it only updates the git index. The actual on-disk bytes stayed CRLF until each file was deleted and re-`git checkout --`'d (git's mtime/content-equivalence check apparently short-circuits an in-place rewrite otherwise). Documented this two-step (`renormalize` + force-recheckout) explicitly in `docs/SETUP.md` §5b and `INSTALL.md`, matching the phiếu's own Nghiệm thu note about this exact gotcha.

## Edge cases / limitations found

- Stub-detection heuristic is a heuristic, not a certainty — a legitimate short single-line no-whitespace text file starting with `.` or `/` under one of the three scanned subdirs would false-positive. Judged acceptable (warn-only, not a hard block) given the scanned subdirs' known content shape (markdown/SKILL.md, always >500 bytes in practice).
- `parity.rs`'s own `run_git()` test-fixture helper (used by `build_sync_fixture`) still emits the Windows CRLF warning to inherited stdio during test runs — harmless (not captured by the parity assertion, `.status()` not `.output()`) and out of Task 2's scope (Files cần sửa lists `new.rs`/`adopt.rs` only, not `tests/parity.rs`).
- `.claude/agents/*.md` on THIS Windows checkout were observed to already contain real full-size content (not stubs) despite `git ls-files -s` showing mode `120000` and `core.symlinks=false` — likely a leftover from earlier ad-hoc dogfood work on this machine, not a reproducible git behavior. `.claude/skills/*` on the same checkout ARE stubs (verified, anchor #5). This inconsistency doesn't affect the fix (the stub-check is heuristic-driven per-file, handles either state correctly) but is noted for anyone auditing this specific checkout.
