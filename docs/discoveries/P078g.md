## Render-route decision (Constraint 1)

**Decision: EMBEDDED-ARTIFACT, engine-side, compile-time.**

`const EMBEDDED_PRE_COMMIT: &str = include_str!("../../../hooks/pre-commit");` (+ `EMBEDDED_PRE_PUSH`) bakes the kit-source hook scripts directly into the `sos-install` crate binary. A new `render_embedded_hooks()` writes them into `project_root/hooks/` inside `engine::apply()`'s success-path, immediately before the existing `arm_git_hooks()` call.

**Why not the two alternatives the phiếu's original prose suggested:**
- **NOT `new.rs`-style `SOS_KIT_DIR`-copy** — that mechanism doesn't exist for `install` (Anchor #4). Building it would mean either (a) requiring `install` to always run inside/near a kit checkout (breaks the standalone-install use case that's the whole point of `sos install` vs `sos new`), or (b) inventing a NEW kit-source-resolution mechanism from scratch — out of scope, and a much bigger surface than this phiếu's stated fix.
- **NOT per-adapter `plan()` artifact** — `ClaudeAdapter::plan()` is a stub; adding hooks there would do nothing for `--runtime claude` today, defeating the "symmetric for both runtimes" constraint. Even for Codex, routing through `plan()` would require the CLI to somehow inject the SAME embedded content into two independent adapter crates rather than one shared engine location.

**Why embedded-artifact wins:** it's self-contained (no external kit-source dependency at install time — the binary itself IS the distribution unit), and it's trivially symmetric because it lives in the one shared `engine::apply()` call-site both `--runtime claude` and `--runtime codex` already funnel through (`crates/sos-cli/src/commands/install.rs`'s `run_adapter()`, confirmed unchanged this phiếu — no new runtime branch introduced).

## End-to-end block test vs. fallback (Nghiệm thu trade-off)

**Achieved full end-to-end**, not the file-existence fallback. `hooks/pre-commit` is an 8-phase gate where 7 phases gracefully WARN-skip when their supporting script/config is absent (by the hook's own design — see its comments), and only `[7/8]` (`scripts/block-env-commit.sh`) is both (a) self-contained (no dependency beyond `git diff --cached`) and (b) exactly the boundary this phiếu is about. The test copies ONLY that one script into the temp fixture's `scripts/` dir, then runs a REAL `git commit` of a REAL `.env` file through the REAL armed `core.hooksPath` — genuinely blocked (non-zero exit, `BLOCKED` message in stderr, commit does not land in `git log`). A clean-file commit through the same armed chain is the negative control (passes), proving the gate isn't always-red. This avoided dragging in the full `security-gate.sh`/`docs-gate` machinery (heavier, and unrelated to what P078g fixes) while still exercising the REAL hook binary end-to-end, not a mock.

## What changed

- **`crates/sos-install/src/engine.rs`**:
  - New `EMBEDDED_PRE_COMMIT` / `EMBEDDED_PRE_PUSH` consts (`include_str!`).
  - New `render_embedded_hooks(project_root)` — writes both scripts, non-clobber (skip+warn if target exists with different content).
  - New `hooks_present_and_executable(project_root)` — existence + (unix) executable-bit check for both scripts.
  - `arm_git_hooks()` changed from module-private `fn` to `pub fn` (so the install-smoke test can exercise the refuse-when-absent guard in isolation, without going through the full render step) and gained a new guard right before `git_config_set(hooksPath, "hooks")`: if `hooks_present_and_executable()` is false, print a loud stderr warning and `bail!` (`Err`) instead of arming.
  - `apply()`'s success-path now calls `render_embedded_hooks(project_root)?;` immediately before the existing `arm_git_hooks(project_root)?;`.
  - No existing public function signature changed (`apply()` still returns `Result<ApplyReport>`).
- **`crates/sos-install/tests/install.rs`** — 5 new tests, all using a `Plan` with ZERO hook-related ops (`empty_plan()`), fixing P078f's structural-oracle-gap:
  1. `install_renders_real_hook_scripts_from_embedded_kit_source_fresh_no_seed` — byte-match to kit source, chmod, hooksPath armed only after render.
  2. `install_end_to_end_blocks_a_real_env_commit_after_fresh_install` — genuine `git commit` block/pass (see above).
  3. `arm_git_hooks_refuses_to_arm_when_hook_scripts_are_absent` — calls `engine::arm_git_hooks()` directly (nothing rendered) → `Err`, `core.hooksPath` stays unset.
  4. `render_embedded_hooks_non_clobber_preserves_customized_hook_content` — pre-seeded custom `hooks/pre-commit` untouched after `apply()`; `hooks/pre-push` (not customized) still renders from kit source; still arms (file exists+executable, even though content differs from embedded).
  - All 10 pre-existing tests (5 general engine + 5 P078f hook-arming) untouched and still green.

## Edge cases / limitations

- **Windows `chmod` no-op:** unchanged from P078f — `#[cfg(not(unix))]` empty body; `hooks_present_and_executable()`'s executable-bit check is also `#[cfg(unix)]`-gated (Windows only checks file existence).
- **Non-clobber at render level is content-based, not identity-based:** a customized `hooks/pre-commit` with content that happens to byte-match kit source is treated as already-correct (no-op, no warning) even if the adopter wrote it independently — indistinguishable from "kit already installed" by design (matches the engine's existing `Decision::NoOp` philosophy elsewhere).
- **Refuse-when-absent is defense-in-depth, not expected to fire in practice:** since the hook scripts are compile-time embedded, `render_embedded_hooks()` always succeeds in producing them (barring a genuine fs write error, which itself already propagates as `Err` before `arm_git_hooks()` is even reached). The `hooks_present_and_executable()` guard mainly protects against future desync (e.g. a future caller invoking `arm_git_hooks()` directly without rendering first) — proven testable now that `arm_git_hooks` is `pub`.
- **Known asymmetry, PRE-EXISTING, explicitly out-of-scope:** `ClaudeAdapter::plan()` renders 0 assets today (Worker CHALLENGE Turn 1, Anchor #3). This is unrelated to hook arming — that happens at the engine level below any adapter's `plan()` output, so `--runtime claude` installs get render+arm exactly like `--runtime codex` even with the stub in place. Fixing the stub itself is a separate, larger surface (out of scope per phiếu Constraint / "Files KHÔNG sửa").
