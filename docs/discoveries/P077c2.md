## Traversal-order finding (Debate Log Turn 1 — the core risk, resolved)

Bash's spine `find` (`bin/sos.sh:1030-1031,1043-1044`) is **UNSORTED** — confirmed via a live probe pre-EXECUTE (creating files in non-alphabetical name order and observing `find` return them in filesystem/creation order, not alphabetical). This is the opposite of `map`'s Bash `scan_files()`, which explicitly pipes through `sort` (and whose Rust port, `map.rs`, correspondingly calls `hits.sort()`).

**Resolution:** `sync.rs`'s walk helpers (`walk_root_files`, `walk_skill_files`, `walk_agents_files`, `walk_commands_files`) deliberately do **NOT** sort — they preserve raw `WalkDir`/`read_dir` enumeration order. Result: `parity_sync_enforced`'s stdout assert passed on the first try with zero order massaging — Rust's `WalkDir` enumeration matched Bash's `find` enumeration bit-for-bit on the same filesystem (macOS/APFS), for the frozen fixture.

**Residual risk (documented, not blocking):** cross-platform (e.g. a future Linux CI runner) order-match between Rust `WalkDir` and Bash `find` is unverified. Not yet load-bearing — no CI workflow currently wires `cargo test` for `bootstrap/sos-rs` (checked `.github/workflows/*.yml`, no hits). If/when CI is added for this crate, re-verify order-match on that platform before treating this as settled; `sync.tree.golden` (the file-content oracle) is immune to this risk by design (frozen sorted).

## Negative test — tree-manifest assert catches file-op regressions

Sabotaged `sync.rs`'s FLAGGED branch to skip the actual `fs::copy` into `.sos-sync-incoming/` while still reporting `FLAGGED` in stdout (mimics "report says it happened, file wasn't written" — the exact false-green class this two-fixture oracle exists to prevent):

```
test parity_sync_enforced ... FAILED
assertion `left == right` failed: sync file-tree manifest mismatch vs sync.tree.golden (hard-fail — sync is PARITY_ENFORCED)
  left:  ... (missing INCOMING line)
  right: ... ADDED/UPDATED/INCOMING (golden, with INCOMING line)
```

Confirmed the failure fired specifically on the **tree-manifest** assert (stdout was unaffected — stdout still correctly said `FLAGGED: 1`, since only the report-string logic wasn't touched, only the file copy was skipped). This proves the oracle catches exactly the regression class it was designed for. Reverted (`mv sync.rs.bak sync.rs`, `touch` to avoid stale-mtime false-negative per c1's documented gotcha), re-ran: all 3 tests green again.

## Re-froze `sync.golden` — scenario-change justification

**Not additive** (unlike c1's `map.agent_map.golden`, which was a pure addition). The original `sync.golden` (real-sos-kit-HEAD, 0-change) is **replaced** by a synthetic-fake-kit, 4-outcome scenario. Justification: the original golden exercised ZERO of `sos_sync`'s actual classification/file-copy logic (0 ADDED/UPDATED/FLAGGED means `_sync_one`'s branch logic for those 3 cases was never hit by the oracle) — this is the same false-green class OA-02/c1 already fixed for `map` (oracle blind to the command's real work). The re-froze is a strict coverage improvement: old golden covered 1 outcome (ALREADY-CURRENT, trivially via `cmp -s`), new golden covers all 4 defined outcomes, and additionally eliminates the real-sos-kit-HEAD dependency flagged as a regression risk in `tests/README.md`'s prior "HEAD-pin caveat" section (now replaced).
