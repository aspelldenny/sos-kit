SOS Kit v3 is a coherent, usable harness for an experienced solo developer who already has working agent delegation and project verification commands. Its strongest contribution is the combination of clear responsibility, independent evidence, and portable mechanical checks. I would adopt its core after fixing installation and health-check gaps, but would not yet recommend it as a turnkey harness for every project.

**What earns its place**
The shared contract is good engineering guidance. [CONTRACT.md](/Users/nguyenhuuanh/sos-kit/harness-lite/CONTRACT.md:21) requires findings to close through affected verification or counterevidence, distinguishes implementation from combined-candidate readiness, and requires independently computed expectations. These rules address real agent failures without restoring tickets and approval ceremony.
The reviewer’s fresh context, original acceptance criteria, delayed exposure to the builder’s verdict, and attention to persistence and exported content are valuable. Keeping the advisor separate from independent review is also correct.
The code has a sensible division: Rust gates, neutral scripts, and small agent adapters. Reading staged content—including staged configuration—is an important detail, with meaningful regression tests in `crates/sos-gates/tests/staged.rs`. Rejecting unknown configuration keys and blocking when gitleaks is unavailable deserve preservation.
Embedded installation assets, explicit file ownership, hashes, dry runs, and preservation of local edits are good foundations. The research also candidly records failures and unmeasured outcomes; that honesty is more useful than productivity claims.
**Weaknesses, ordered by impact**
1. **Installation can silently disable existing protection.** [kit.rs](/Users/nguyenhuuanh/sos-kit/crates/sos-cli/src/kit.rs:357) preserves an existing `core.hooksPath`, but does not inspect ordinary `.git/hooks/` when that setting is absent. It then redirects all hooks to `harness-lite/hooks`, disabling any existing pre-commit, pre-push, or other hooks there. This contradicts the preservation intent and is the first defect I would fix. Installation is also incremental: an error after writing the manifest can leave a partially installed repository that refuses another `sos install`.
2. **“Installed” and “healthy” are too easy to confuse with “adopted.”** The template references `docs/BACKLOG.md` and `docs/FEATURES.json`, but installation creates neither and supplies no feature-schema example. [check](/Users/nguyenhuuanh/sos-kit/crates/sos-cli/src/kit.rs:432) checks a pre-commit substring, does not require pre-push to invoke local-secret scanning, and detects agent wiring through string presence rather than parsed configuration. It does not check the Claude import or unresolved project placeholders. README additionally advertises type checks, while installed app hooks contain none; those belong to project-local hooks. `make ready`, central to the research’s readiness argument, remains an example placeholder.
3. **The execution model is less portable than the gates.** The main session must delegate and cannot implement product code; without delegation, [orchestrator.md](/Users/nguyenhuuanh/sos-kit/harness-lite/roles/orchestrator.md:15) tells it to report a capability limit. That makes routine work unnecessarily expensive and excludes otherwise capable single-agent runtimes. The reviewer says to report inability to run the artifact “rather than reviewing statically,” weakening support for infrastructure, libraries, and document review. Writing has no criteria for source accuracy, argument, voice, or publication output. `docs/BACKLOG.md` acknowledges profiles are unfinished.
4. **Advisor behavior and cost are underspecified.** The worker describes a transcript-reading advisor, but [scripts/advise](/Users/nguyenhuuanh/sos-kit/scripts/advise:27) sends an optional brief, error tail, status, recent commits, and truncated diff. On a clean tree, the tool-less Claude advisor receives no implementation; a saved sample consequently guesses the wrong week boundary. App templates enable automatic calls by default, using Claude/Opus even for Codex users. Native advisor guidance and automatic advice can overlap. `test-watch.py` counts failures across test commands, resets on any detected success, and silently suppresses internal errors. Its stop instruction is guidance, despite stronger README wording.
5. **Recipe confidence exceeds recipe verification.** The library preserves useful experience, but its anchors mostly prove strings exist. In [payos-vn.md](/Users/nguyenhuuanh/sos-kit/recipes/payment/payos-vn.md:298), the raw-HMAC “FAIL” command still exits successfully; plain `curl` does not assert the expected HTTP status. Payment settlement also lacks an explicit comparison between webhook amount and the stored order amount. The “sliding-window” limiter actually resets a fixed window and never evicts inactive keys. Required recipes and source tests sometimes exist only as TODOs or private `~/tarot` references. “Battle-tested” source code does not validate an adapted example.
6. **Maintenance safeguards lag behind the distribution model.** The only workflow, [release.yml](/Users/nguyenhuuanh/sos-kit/.github/workflows/release.yml:32), builds binaries without running tests; there is no PR test workflow. Project-owned wrappers and settings require manual migration indefinitely. An existing `.sos-new` is preserved even when a later upstream version arrives, so its proposal can become stale while manifest metadata advances. README still says the release is unpublished. These are precisely the integration and documentation failures v3 claims to address.
7. **The economy claim remains unproven.** The contract is 960 words and the orchestrator adds 726; short line counts conceal substantial instructions. Mandatory delegation and review triggers for almost every stored-data change can dominate that prompt cost. The advisor lab is one easy problem per configuration, while current real-project usage measurements remain backlog work. The feature gate preserves IDs but permits rewritten titles and verification steps; `passes` has no revision/environment binding, and permanent IDs have no retirement policy. It protects bookkeeping, not current acceptance evidence.
**Next upgrades, ordered by value per effort**
1. **Repair hook preservation and installation preflight—roughly 1–2 days.** Inspect effective hooks, including Git’s default directory; propose explicit chaining. Validate every destination before mutation and make interrupted installation recoverable. Add fixtures for existing ordinary hooks and partial failures.
2. **Make onboarding concrete—roughly one day.** Remove stale release wording, document what each gate actually runs, provide a feature example and first-task walkthrough, and either create minimal state files or clearly require their selection. Validate imports, JSON wiring, both hooks, placeholders, and required referenced paths.
3. **Add PR and release verification—roughly one day.** Run Rust and adapter tests on supported platforms, then install the built binary into scratch repositories and exercise actual commit/push failures. Use locked dependency resolution for releases.
4. **Permit one implementing agent and add small project profiles—roughly 1–2 days initially.** Delegate when isolation or parallelism pays; retain fresh review at consequential boundaries. Start with writing and CLI profiles, including artifact-specific acceptance checks and a practical readiness command.
5. **Make advice explicit and measurable—roughly 1–2 days.** Select the backend during adoption, expose unavailable advice, distinguish native from snapshot advice, and supply relevant bounded source context. Record calls, usage, latency, and changed decisions before choosing defaults.
6. **Replace recipe anchors with executable behavioral examples—several days, starting with payments.** Assert invalid input, settlement mismatches, duplicate delivery, concurrency, and failure recovery. Publish the required tests and compatibility assumptions alongside each recipe.
**What I would remove**
Remove mandatory delegation for routine edits, universal mobile/simulator language from core roles, the default vendor-name blacklist from general projects, and “stable/battle-tested” labels unsupported by reproducible recipe checks. Archive remaining live v2 fossils and stale procedural references. Keep the four roles, but make their use earn its cost.
