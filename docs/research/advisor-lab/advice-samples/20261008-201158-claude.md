# advice (claude default, 18s, rc=0)

**Q:** Tests fail. Root cause, and should I change approach?

VERDICT: change approach

WHY: There are two separate bugs in `weekly_pay` (pay.py), and the numbers in the failures point straight at each one.
- **`test_shift_crossing_week_boundary` (test_pay.py:15):** the result 104000 equals 40×2000 + 8×3000. All 48 hours landed in one week, so 8 hours were paid as overtime when 4 should have been. The code gives a whole shift to the week it started in instead of splitting it at the week boundary.
- **`test_fractional_cents` (test_pay.py:18):** 9 minutes × 1999 / 60 = 299.85, and the code returned 299. That means it floor-divides (truncates). It should round half up, once per week, on the exact total. If it also rounds regular and overtime pay separately, the errors add up.

NEXT:
1. In `weekly_pay`, split each shift at every week boundary it crosses. Use a loop, so a shift spanning several boundaries also works. Add each piece's minutes to the week it falls in. Before coding, check which day the week starts on in pay.py or the spec. Earlier runs used Sunday 00:00.
2. For each week, work out regular and overtime minutes, then do all the maths in integers: `num = reg*rate*2 + ot*rate*3`, pay = `(num + 60) // 120`. Round only once per week. Don't use floats or `round()`, because `round()` rounds halves to even, not up.
3. Run `python3 -m unittest test_pay` and don't edit the tests.

RISKS:
- A shift that ends exactly at the week boundary must not create an empty piece in the next week, or one that counts as zero-length overtime.
- Shifts may arrive out of order. Group them by week, not by the order they appear in the list.
- If the 40-hour limit is checked per shift instead of per week, you get the same kind of bug as the boundary one.
- Timezone-aware datetimes and daylight-saving changes aren't tested. Leave them out of scope and say so.
- Other code that calls `weekly_pay` may rely on it returning an int. Keep returning an int.

CHECK: `python3 -m unittest test_pay` shows "Ran 4 tests … OK". Also check by hand that the boundary case comes to exactly 100000 and the 9-minute case to exactly 300.
