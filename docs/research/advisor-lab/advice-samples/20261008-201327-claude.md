**Q:** Tests fail. Root cause, and should I change approach?

VERDICT: change approach

WHY: The code has two separate bugs. Each test shows one of them.
- `test_shift_crossing_week_boundary` (test_pay.py:15) gets 104000. That equals 40×2000 + 8×3000, so all 48 hours landed in one week and 8 became overtime. Expected is 44h in one week (4h overtime) and 4h in the next. `weekly_pay` buckets a shift by its start time and never splits it at the week boundary.
- `test_fractional_cents` (test_pay.py:18) checks 9 min at 1999¢/h, which is 299.85¢. The code returns 299 because it floors. The spec wants half-up rounding, done once per week on the exact total. Rounding the regular and overtime parts separately will also drift.

NEXT:
1. Find the week-start rule in `pay.py` or its spec. Prior runs in `evidence/e2e.json` used Sunday 00:00, but confirm it. Split each shift at every boundary it crosses, using a loop rather than a single split. Accumulate minutes per week.
2. For each week, set regular = min(minutes, 2400) and overtime = the remainder. Compute pay in pure integers as `(reg*rate*2 + ot*rate*3 + 60) // 120`. Do not use floats or a separate floor for each part.
3. Don't edit the tests. Leave `evidence/` alone, since that is unrelated harness churn in git status.

RISKS:
- A shift ending exactly at the boundary must not create a zero-minute bucket in the next week.
- A shift can span more than one boundary.
- Weeks are separate: the overtime threshold resets every week, and rounding happens per week, not once over the grand total. Check what the function's return contract expects when there are several weeks.
- Seconds or microseconds in datetimes: decide whether to truncate to minutes or keep exact time.
- Timezone-aware datetimes or DST, if any callers pass them.
- Other callers of any helper you change.

CHECK: `python3 -m unittest test_pay -v` passes all 4 tests. Also run one ad-hoc case: a shift ending exactly at the week boundary gives the same total as the same hours inside one week.
